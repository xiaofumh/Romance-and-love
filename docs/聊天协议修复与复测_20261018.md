# 聊天协议修复与复测

日期：2026-10-18，北京时间。工程：`项目根目录`。未上传、部署或发布，不改动现有用户聊天与授权。

## 修复结论

已修复本轮发现的模型聊天输出协议冲突。不是关闭输出校验，也不是通过追加模型调用来重试凑成功。

此前50次真实API均返回HTTP200，但只有6轮被应用接收；带历史的44轮均发生`INVALID_MODEL_OUTPUT`。捕获到的43条失败响应是自然纯文本，适配器却执行JSON.parse。历史assistant也以纯文本回填，系统提示同时要求JSON，这个组合没有稳定满足契约。

本补丁让普通聊天的外部传输与历史保持同一种格式，不再要求模型将一句聊天包进JSON。没有单独证明“提示词”和“历史序列化”各自的因果贡献，不声称只有一个因素导致问题，也不声称GLM完全不支持JSON。

| 层级/任务 | 当前格式与校验 |
| --- | --- |
| 外部模型陪伴聊天 | 明确请求`response_format: {type: 'text'}`，系统提示仅输出纯文本 |
| 历史assistant消息 | 直接保留此前聊天正文，不加JSON外壳 |
| 服务端业务接口 | 适配器包装为`{text}`，执行严格schema及1至1200字限制，随后继续内容审核与事务归属验证 |
| 旧模型结果兼容 | 仅接受严格单字段`{text:string}`，空值、超长、类型错误或额外字段仍拒绝 |
| 旧版三条回复建议 | 仍请求JSON，继续JSON.parse及三条建议结构校验，不受本次聊天变更影响 |

服务端仍检查HTTP状态、完整`finish_reason: stop`、字符串content和100KB响应上限；没有放宽超时、用户/角色隔离、审核、预算、幂等与删除后取消。没有使用eval或修补损坏JSON。
