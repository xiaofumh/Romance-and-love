# V0.7研发版：30天聊天独立存储

2026年10月30日，0.7.0-dev.1。代码与离线验证完成不代表云端已部署；本轮保持活动工程、云端密钥和已发布版本不变。

## 产品规则

- 云端聊天正文按每条消息的服务器时间保存最近30×24小时，不再按40条截断。用户主动清理、关联资料删除等隐私操作仍可提前删除。
- 最近12轮是模型输入窗口，不是数据库保留条数。保存30天不表示模型每轮读完整30天，也不保证对窗口外内容自动召回。当前仍主要检索已确认记忆，没有新增向量或完整历史语义检索。
- 页面初始显示最近40条，可点击“查看较早聊天”继续分页；40是页面大小，不是保存上限。
- 云端近期工作缓存为60条语义消息，足够覆盖现有每用户轮普通回复及最多3次主动尝试的最近12轮。工作缓存淘汰不删除独立归档；每条历史600字符的模型输入预算保持。
- 角色、记忆、参考资料等仍保留4MB陪伴状态/5MB用户状态保护。独立聊天正文不计入这两个状态阈值，但仍占实际云数据库空间、读写额度和导出设备空间。不是无限容量或无限免费承诺。
- 本地演示也取消40条截断，但受设备存储限制；空间失败保留原快照并报错，不悄悄删旧聊天。

## 模块与数据结构

| 文件/集合 | 责任 |
|---|---|
| `src/shared/history.ts` | 统一30天期限、40条页面、60条工作缓存、迁移批次和游标类型 |
| `src/cloud/history-storage.ts` | 用户状态/工作缓存/正文的原子保存、旧数据兼容迁移、分页与单消息读取 |
| `src/cloud/repository.ts` | 每次事务先读工作缓存，执行业务与清理，再一起提交；根状态不复制归档正文 |
| `src/cloud/history-cleanup.ts` | 删除队列与到期消息的有界物理清理 |
| `src/server/companion.ts` | 取消条数截断；历史分页/来源读取；模型仍使用selectContext |
| `src/miniprogram/pages/chat/` | 分页展示、去重、顶部锚点、隐私变更后拒绝迟到页面 |
| `src/miniprogram/services/history-export.ts` | 每次一页追加JSON，避免一次装入全部历史 |
| `assistant_chat_messages` | 每条消息独立记录：所有者、会话、历史版本、序号、正文、到期时间 |
| `assistant_chat_tails` | 当前版本最近60条工作缓存；账号根文档只保存历史版本和下一个序号 |
| `assistant_chat_cleanup` | 不含聊天正文的旧版本清理任务 |

消息ID、缓存ID与清理任务ID采用服务端用户标识、会话、历史版本和记录标识计算摘要。客户端不能通过传入其他用户ID选择数据范围。分页查询同时约束用户、会话和版本，返回前再核对版本，单消息读取也检查归属与期限。

## 保存、迁移和失败处理

消息写入、工作缓存及账号状态在同一数据库事务提交。不能先删根文档里的旧正文，再尝试异步补写归档。任何一个写入失败，整个事务回滚。

旧版仍存在的40条正文按批次迁入；一次最多60条迁移消息，并控制总写入预算。多个旧会话可在后续事务逐步迁移；未完成者继续使用旧正文结构，不留下没有正文的归档指针。新比较会话优先处理，避免复制旧历史指针却没有复制正文。

旧版已经按40条规则丢掉的记录不能恢复。源码备份不等于聊天数据备份。上线前须保存现有业务数据快照，检查实际SDK事务语义、失败回滚与迁移完整性。旧云代码不能管理新归档，回滚方案必须保留兼容读取器或先停写，不能仅替换代码后宣称归档仍可正常工作。

当旧成功请求的正文不在工作缓存时，原请求查询不再次调用付费模型，并提示从30天历史查看。请求幂等与状态保留仍为原48小时策略，不宣称延长到30天。

## 删除与到期

清空正文时递增历史版本，旧分页游标立刻失效；删除会话后无法再通过历史API访问它。旧版本正文与缓存加入清理队列，每次最多处理5个任务、每任务20条正文；到期消息每次最多40条。队列和定时任务积压会影响物理清理完成时间，不承诺精确到秒。

服务端在分页和单消息读取时始终过滤已到期消息，即使物理清理尚未执行也不返回。账号状态定时维护会同步清理到期工作缓存。仍需部署实际清理触发器并监控积压。

会话元数据记录曾引用的文档ID，避免只有近期缓存被检查，导致较早归档引用在资料删除后重新出现。来源消息可在30天归档中读取；超过期限如实提示原文不可用，不用摘要冒充。

## 分页与导出

历史页使用“版本＋上一页最早消息ID”的游标，按单调序号查询，不采用容易受新消息影响的offset。页面合并按消息ID去重，加载旧页不把正文作为模型输入上传。隐私变更或版本改变后丢弃迟到结果。

用户确认导出后，先写角色/资料等元数据，再逐会话、逐页追加正文。JSON格式为`chat-history-v2`，消息顺序明确为`newest-first`。导出失败停止分享并删除未完成文件；新生成消息按导出起始时间过滤。不是所有资料的跨事务原子快照。

## 部署准备（尚未执行）

1. 创建上述三个集合，客户端读写权限均设为禁止，仅允许服务端云函数通过可信身份访问。
2. 为消息集合建立适合`ownerId + conversationId + epoch + sequence(desc)`的复合索引，并结合`expiresAt`过滤验证实际执行计划；到期清理需要`expiresAt`索引。不得用开放数据库权限解决索引错误。
3. 同版本部署API、清理函数和前端；验证分页查询、事务操作数、写冲突重试和返回形状。实际SDK与部署环境尚未验收，不因类型检查通过作出上线保证。
4. 使用说明版本为`2026-10-30.v0.7-history30d`。旧用户后续生成前需要自行确认新的30天保存说明，不自动代替用户勾选；现有记录仍可查看与删除。
5. 用合成会话验证超过40条、重启后读取、双微信身份、30天边界和删除，然后制作扫码体验包。未完成前保持研发分支，不替换当前发布版。

## 验证范围

离线测试覆盖160条归档及完整分页、超过5MB的总归档不撑大根状态、12轮模型窗口、旧记录原子迁移与失败回滚、归档/缓存/根写入一致性、过期过滤及分批清理、删除版本失效、来源跨缓存读取、跨用户拒绝、分页导出和页面迟到结果。

这些是合成数据与SDK边界替身测试，不是实际云端容量或真实GLM质量测试。真实云迁移、权限、索引、清理触发器、设备文件系统和跨天运行仍需验收。
